# 自適應候選詞庫與可選人工覆核

此功能是本機 Python / Ollama-compatible 研究流程的一部分。**LLM 提出的中文字始終是未驗證假說，絕不等於破解碼組**。

## 操作模式

GUI「推論與解讀」→「候選詞庫更新／人工覆核」提供三種模式：

- **維持既有詞庫**（static）：預設相容舊流程。允許 0 回合離線分析，或 1～20 回合在既有詞庫內提出碼組候選，不額外生成新詞。
- **逐回合擴充，自動採納**（automatic）：每回合在送出碼組推理提示前，先呼叫經允許的內網 LLM 生成新候選，依界限自動加入弱先驗詞庫，再重新求解並提出碼組候選。**無人工覆核等待**，可一次連續完成 1～20 回合。
- **逐回合擴充，人工覆核**（human）：每回合產生新詞後將工作狀態設為 `awaiting_review`，UI 顯示候選詞及來源理由，可勾選任何子集合或全部拒絕；核准後繼續。同一工作在等待審核期間阻止其他分析與模型設定切換。十分鐘內沒有回應則失敗，不會自動接受。

後兩種模式需要至少 1 回合、每回合**兩次** LLM 請求：第一個產生新候選詞，第二個對現有碼組候選提出建議。回合數和模型耗時會相應增加。

## 每輪使用的證據及限制

`adaptive_vocabulary.py` 透過 `safe_llm_message` 僅傳送合法密碼組及明確允許的輔助欄位；同時傳送整個案例的碼組頻率、時間關聯假說（保留無關選項）、上一輪未驗證碼組假說、可信逐碼錨點及現有詞庫。0 輪或關閉元數據不呼叫相應資訊。模型回傳的新詞及理由經格式驗證、去重後才可加入詞庫。

- 每回合最多**32 個**新詞；每次執行最多保留 **128 個**動態新增詞。追加到執行內存中的 `llm_dynamic_candidates` 弱先驗詞庫，不自動覆寫研究員的案例、驗證錨點或原始人工詞庫。
- 自動模式只表示**不阻塞人為審核**，並不代表新詞已證實。重複碼組／可信已知明文由核心求解器維護。
- LLM 端點安全規則不變：本機／明確核准的 RFC1918 私網地址，不准公網端點；完整 Prompt/回覆只有使用者主動選取擷取選項才會寫入 SQLite。
- 執行工作使用啟動時的**案例快照**。假設研究員在執行中新增第三方情報，系統不會偷偷改動正在跑的 job，應重新啟動一輪分析才能使用新情報。這與「在每一輪看到新的推論結果、動態修改詞庫」不同。
- 模型呼叫失敗或回傳錯誤格式時不採用未審核詞彙，也不偷偷使用合成真值當備援詞庫。

## API／測試

`POST /api/start` 新增 `candidate_mode`：`static`、`automatic`、`human`，預設 `static`。

人工審核時 `GET /api/jobs/{job_id}` 回傳 `status: awaiting_review` 和 `pending_review: {round,candidates}`；`POST /api/jobs/{job_id}/review` body 為 `{"approved": ["候選詞一", ...]}`。核准詞必須包含於當前待審項目，提交一次即鎖定；候選全拒絕可使用空陣列。

`python -m unittest discover -s tests -v` 覆蓋詞庫迭代、來源安全、手動拒絕與舊模式相容性。所有修改以 PR 為準，未通過 Hosted CI／Codex Review 前不得合併。
